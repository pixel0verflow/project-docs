peonmaxxer-testing-facility

github.com/pixel0verflow/peonmaxxer-testing-facility · public

1. Problem statement — why?

peonmaxxer runs coding agents unattended, but "which model is worth running?" was answered by anecdote. This facility turns it into a repeatable benchmark: three fixed tasks, one command per model per run, every result a PR whose first line states model, API-vs-local (with machine specs when local), harness, wall-clock time and token totals — comparable at a glance across models.

2. Features

  • Three benchmark tasks under src/benchmark/: task1 RecurKit (Swift) — find & fix a planted bug from a user report, with no shipped test for it (the model writes the reproducing check; suite is a framework-free runner so bare Command Line Tools suffice); task2 logstat (Rust, std-only) — implement a spec'd log-analysis CLI against byte-exact goldens; task3 pricing-site (Svelte 5 + Vite) — build a product site around a test-pinned pricing engine (marginal volume tiers, annual discount, half-up rounding). All three contracts proven satisfiable by throwaway reference implementations before landing.
  • Per-model run generator scripts/new-benchmark-run.sh: interactive picker over opencode models, generates a per-model workflow (model is static per workflow — peonmaxxer can't vary it per run yet), registers it in peonmaxxer.yaml, emits numbered tasks (BENCH-<run><task>), copies scaffolds to src/<slug>/r<run>/, commits. Rerunnable by construction.
  • Workflow shape (10 steps): scaffold-check → implement → verify (goto-fix loop) → push → PR → fresh-session adversarial review (read-only, diff-fed, forced REVIEW VERDICT:) → apply fixes → verify → push → PR update.
  • PR stats convention: line 1 = model · locality · harness · time · tokens; scripts/stamp-pr-stats.sh fills time/tokens from the core's API post-run (the workflow template context exposes no run stats).

3. Architecture overview

A consumer project of peonmaxxer-core: peonmaxxer.yaml (auto-activating backlog, gate protecting src/benchmark/, scripts and config), generated workflows in .peonmaxxer/workflows/, generated tasks in .peonmaxxer/backlog/. Verify gates keep caches in-tree (.npmrc, std-only Rust) so peonmaxxer's sandboxes can run them.

Model per workflow, not per runWorkflows pin the model statically; the generator works around it with one workflow per model.
