finbrake

Per-customer fund-load velocity limiter · 🔵 Complete (take-home)

1. Problem statement — why?

A service must decide, in real time, whether to accept or decline a customer's attempt to load funds, enforcing per-customer velocity limits. Built as a take-home exercise; the goal was a clean, well-tested implementation of the rules below with a maintainable architecture.

Velocity rules (per customer):

  • max $5,000 loaded per UTC day
  • max $20,000 loaded per ISO week (Mon 00:00 UTC → next Mon)
  • max 3 loads per UTC day, regardless of amount

Declined attempts don't consume budget. Repeated (customer_id, id) pairs are silently ignored after the first occurrence (idempotency).

2. Features

  • REST mode (default): POST /load-attempts → 200 with decision, 204 for duplicates, 400 for malformed input.
  • CLI mode: CommandLineRunner gated on finbrake.input, replays a fixture file to stdout/file.
  • Three velocity rules with accepted-only window aggregation.
  • Full audit trail — both accepted and declined attempts persisted; window queries filter to accepted=true.
  • DB-level dedup via composite uniqueness on (customer_id, attempt_id).

3. Architecture overview

Ports & adapters (hexagonal). Spring Boot 4 on Java 25 (Jackson 3). Domain is pure Java with no framework deps; Spring concerns live only at the application/adapter boundary.

adapter/in (web, cli) ──▶ application (port.in)
                               │
                               ▼
                        application service ──▶ domain (LoadAttempt, VelocityPolicy, TimeWindows)
                               │
                               ▼
                        application (port.out) ◀── adapter/out (JPA persistence)
LayerContents
domainLoadAttempt, LoadDecision, VelocityPolicy (static rules), TimeWindows (UTC day / ISO week)
applicationLoadAttemptService + inbound port ProcessLoadAttempt + outbound port LoadAttemptStore
adapter/inREST controller + DTOs + exception handler; CLI file runner
adapter/outJPA entity + Spring Data repo + store adapter (H2 in-memory)

Service flow: dedup check → compute daily-amount / daily-count / weekly-amount (accepted only) → VelocityPolicy.accepts(...) → persist → return decision.

Quality gates: Spotless (Palantir format), Error Prone (main only), SpotBugs (MAX/HIGH), all wired into ./gradlew check. Tests span pure-unit (policy, time windows), service-with-fake-store, @DataJpaTest slice, @WebMvcTest slice, and @SpringBootTest fixture-parity.

4. Problems to solve / known limitations

ItemNotes
In-memory persistenceH2 with ddl-auto=create-drop; no durable store. Swappable by a new LoadAttemptStore impl (the point of the hexagonal design).
Single-node concurrencyWindow aggregates + insert aren't transactionally isolated against concurrent attempts for the same customer; under true concurrency two requests could both read budget then both accept. DB unique constraint guards dedup, not the velocity race. Would need row locking / serialized per-customer processing for production.
Money as primitiveAmounts parsed from $-prefixed strings; fine for the exercise, a dedicated Money type would harden it.
