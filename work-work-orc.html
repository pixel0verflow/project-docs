work-work-orc

Autonomous Claude Code orchestration — spec in, PRs out · 🟢 Active (research phase)

1. Problem statement — why?

Complex projects stall on operator availability: every turn of agent work needs a human at the prompt. The goal is a rig where a specification written before the work starts is enough for Claude Code to work continuously — overnight, or around the clock — with no interactive input, producing reviewable pull requests instead of an unreviewable pile of commits.

The unsolved part is not the loop (Claude Code now ships several). It's making "done" machine-checkable, keeping the agent inside its scope, and making sure a 3am stall is noticed.

2. Features

Research phase — nothing built yet. The findings set (in-repo, not published here) covers:

  • Capability map — every native Claude Code mechanism for unattended work: headless -p, /goal, Stop/StopFailure hooks, background agents and the supervisor daemon, /loop + cron tools, cloud routines, desktop scheduled tasks, dynamic workflows, agent teams, sandboxing tiers, auto mode.
  • Ecosystem patterns — the Ralph loop and what it teaches (the filesystem is the memory), spec-driven development and its documented drift modes, third-party harnesses worth reading before writing one.
  • Proposed architecture — one task = one fresh session = one worktree = one PR, gated by a verifier script the human wrote.
  • Guardrails, cost and failure modes — usage-window math, deny lists, isolation ladder, and the failure table every source converges on.
  • Remote operation — driving and monitoring the rig from a phone.

3. Architecture overview

Spec → queue → worker → gate. State lives on disk so any session can rehydrate from a cold start; context is deliberately short-lived.

spec/ (human-written, once)

        │
        ▼
supervisor  ──picks next unblocked task──▶  claude -p --worktree "/goal <criteria> or stop after N turns"
        ▲                                          │
        │                                   Stop hook runs criteria script
        │                                          │
        └──── pass: commit → branch → PR ──────────┤
              fail: journal + backoff, break after 3
                                                   ▼
                                    state/ progress · journal · QUESTIONS · BLOCKED
PieceRole
spec/criteria/*.shThe only definition of done that counts. Exit 0 = task complete. Human-authored so the agent can't grade its own homework.
/goalNative turn-after-turn loop; a Haiku evaluator judges the condition from the transcript. Cheap second opinion on top of the script.
Stop hookDeterministic gate: runs the criteria script, feeds failures back as the next prompt.
StopFailure hookNight watchman: rate limit / auth / billing errors write BLOCKED.md and notify.
git worktree per taskFile isolation, so parallel or failed tasks never contaminate each other.
QUESTIONS.mdJudgement calls get parked, not guessed. The agent moves to the next unblocked task.

4. Problems to solve / known limitations

ItemNotes
Verification is the ceilingEvery source agrees: autonomy scales with verification quality, not loop cleverness. A project without a trustworthy test suite can't be automated this way — the first build step is the verifier, not the loop.
Usage windows, not dollarsSubscription plans meter on rolling 5-hour and weekly windows shared with chat; parallel sessions multiply consumption roughly linearly. Hard dollar caps (--max-budget-usd) require API-key billing.
Billing vs remote controlPhone steering (Remote Control, cloud sessions) needs subscription login; hard spend caps need an API key. Likely answer is two environments on one machine.
Prose is advisoryMemory files and spec text are followed probabilistically. Anything that must hold has to be a hook or a deny rule.
Spec drift undetectedNo tool in the category ships spec-vs-code drift detection; a periodic re-check of acceptance criteria against HEAD has to be written.
Local scheduling is fragileSession-scoped tasks expire after 7 days, die with the terminal, and never catch up missed fires. Durable scheduling means the background daemon, desktop tasks, cloud routines, or CI.
